# Revised Chapter 3 Blueprint for a Solid Chapter 4

## 1) Revised Problem Statement
Current adaptive web interfaces often optimize engagement or speed without guaranteeing real-time WCAG compliance, and many provide weak human oversight. This can produce unsafe UI adaptations for users with disabilities and reduce user trust.

## 2) Revised Aim
To design and implement an adaptive web interface that uses constrained reinforcement learning with human-in-the-loop (HITL) control to optimize usability while maintaining WCAG-compliant adaptations.

## 3) Revised, Measurable Objectives
1. **Constrained RL module**: Implement a contextual bandit policy for UI adaptation with explicit state variables, action set, and reward/penalty model; target mean cumulative reward improvement of **>=15%** over static baseline.
2. **WCAG gatekeeper module**: Implement pre-deployment compliance checks that block non-compliant actions; target **>=98% WCAG compliance rate** in accepted adaptations.
3. **HITL governance module**: Implement explicit approval workflow (roles, triggers, thresholds, timeout, override, fallback) with full audit trail; target **100% logging coverage** of adaptation decisions.
4. **Controlled evaluation module**: Evaluate in web simulation and report compliance, task completion time, and trust score against targets: compliance **>=98%**, median task time improvement **>=10%**, trust score **>=4.0/5**.

## 4) Implementation-Ready Technical Specification

### 4.1 Chosen Learning Paradigm and Algorithm
- **Paradigm**: **Online contextual bandit** (single-step decision per UI adaptation event).
- **Algorithm**: **LinUCB** (or Thompson Sampling with linear payoff if needed).
- **Justification**: UI adaptation decisions are immediate and context-dependent; delayed long-horizon credit assignment is not required, so contextual bandit is methodologically consistent and simpler than full MDP RL.

### 4.2 State (Context) Space
At each adaptation event `t`, context vector `x_t` contains:
- User profile: assistive technology flag, visual/motor/cognitive preference indicators.
- Session behavior: click latency, error rate, scroll depth, task stage.
- UI environment: current theme, font scale, contrast level, component density.
- Accessibility diagnostics: current WCAG rule risk indicators.

### 4.3 Action Space
Discrete adaptation actions `a_t`:
- `A1`: Increase font size (small step)
- `A2`: Increase contrast theme
- `A3`: Simplify layout (reduce component density)
- `A4`: Increase hit target sizes
- `A5`: Enable reduced motion profile
- `A6`: No change

### 4.4 Reward, Penalty, and Constraint Equations
For chosen action `a_t` under context `x_t`:
- Usability reward:
  - `r_task = +1` if task step completed within threshold, else `0`
  - `r_time = - min(1, completion_time / time_budget)`
  - `r_error = - error_count_normalized`
  - `r_trust = normalized_user_feedback` in `[0,1]`
- Combined base reward:
  - `r_base = 0.4*r_task + 0.2*r_time + 0.2*r_error + 0.2*r_trust`

WCAG constraints:
- Let `v_t` = number of WCAG violations predicted/observed for `(x_t, a_t)`.
- Penalty term: `p_wcag = lambda * v_t`, with `lambda = 2.0` (tunable).
- Final reward to learner:
  - `r_t = r_base - p_wcag`

Hard constraint rule:
- If critical WCAG rule fails (e.g., contrast below threshold), action is **blocked before deployment**.
- Blocked actions are replaced with fallback action and logged as rejection events.

### 4.5 Constraint-Check Logic (Pre-Action Gate)
1. Candidate action generated by policy.
2. WCAG Validator simulates resulting UI state.
3. If any hard-rule violation: reject action, apply fallback (`A6` or safe preset), log reason.
4. If soft-rule warning only: send to HITL based on confidence/impact trigger.
5. Accepted action proceeds to UI renderer.

## 5) System Stack and Modules

### 5.1 Technology Stack
- **Frontend**: React + TypeScript
- **Backend API**: Python FastAPI
- **Policy Service**: Python (NumPy/scikit-learn for LinUCB)
- **Database**: PostgreSQL
- **Event/Log Store**: Structured JSON logs + PostgreSQL audit tables
- **Monitoring**: Prometheus + Grafana (decision latency, compliance rate, block rate)

### 5.2 Core Modules and Interfaces
1. **Context Collector (Frontend -> Backend)**
   - `POST /api/context`
   - Request: `{ user_id, session_id, context_features, ui_state, timestamp }`
   - Response: `{ context_id }`

2. **Policy Decision Service**
   - `POST /api/adapt/decide`
   - Request: `{ context_id, context_features }`
   - Response: `{ action_id, action_payload, confidence }`

3. **WCAG Validator**
   - `POST /api/adapt/validate`
   - Request: `{ context_id, action_payload, ui_snapshot }`
   - Response: `{ status: pass|warn|fail, violations, severity }`

4. **HITL Review Service**
   - `POST /api/hitl/review`
   - Request: `{ context_id, action_payload, confidence, validation_result }`
   - Response: `{ decision: approve|reject|override, reviewer_id, reason }`

5. **Adaptation Executor**
   - `POST /api/adapt/execute`
   - Request: `{ context_id, approved_action }`
   - Response: `{ execution_status, applied_ui_state }`

6. **Learning Update Service**
   - `POST /api/policy/update`
   - Request: `{ context_id, action_id, reward_components, wcag_violations, final_reward }`
   - Response: `{ model_version, update_status }`

## 6) End-to-End Request/Response Flow
1. Frontend captures context and posts to `/api/context`.
2. Policy service selects candidate action.
3. WCAG validator checks candidate action.
4. If `fail` -> block and fallback; else evaluate HITL trigger.
5. If HITL required -> reviewer decision.
6. Approved action executed on frontend.
7. Outcome metrics collected (time, errors, trust feedback).
8. Final reward computed and used to update policy.
9. All events persisted to audit tables and monitoring dashboards.

## 7) Methodologically Consistent Experimental Design

### 7.1 Data Split Policy
- **No supervised 80:20 train/test split** for online contextual bandit learning.
- Use **phased online evaluation**:
  - Phase A: Warm-up with safe defaults + limited exploration.
  - Phase B: Controlled online learning episodes.
  - Phase C: Frozen-policy test window for unbiased evaluation.

### 7.2 Episodes, Checkpoints, and Stopping Criteria
- Episode = fixed number of adaptation events (e.g., 200 events).
- Validation checkpoint every 5 episodes.
- Stop when one occurs:
  1. Reward improvement <1% across 3 consecutive checkpoints.
  2. Compliance rate drops below 98% for 2 consecutive checkpoints.
  3. Maximum episodes reached (e.g., 60).

### 7.3 Test Procedure
- Freeze best policy version selected by validation criteria.
- Run A/B comparison against static baseline and rule-based baseline in matched tasks.
- Collect: WCAG compliance, completion time, error rate, trust score.

### 7.4 Metrics and Statistical Tests
- Compliance rate: proportion test (z-test for proportions).
- Completion time: Mann-Whitney U (non-parametric) or t-test if normality holds.
- Trust score: Mann-Whitney U / ordinal analysis.
- Report effect sizes and 95% confidence intervals.

## 8) Fully Defined HITL Governance

### 8.1 Roles
- **Accessibility Reviewer**: primary approver for flagged adaptations.
- **Product Owner**: override authority for exceptional cases.
- **System**: auto-approves low-risk actions meeting thresholds.

### 8.2 Approval Triggers
HITL review required if any condition is true:
- Policy confidence `< 0.60`
- Validator status is `warn`
- High-impact UI regions are affected (navigation/forms)
- User belongs to vulnerable accessibility profile and action is non-trivial

### 8.3 Decision Rules
- Approve if no hard violation and expected utility gain >= 5%.
- Reject if potential WCAG regression exists.
- Override allowed only by Product Owner with mandatory reason log.

### 8.4 Timeout and Latency Rules
- Reviewer SLA: 2 seconds in simulation / 30 seconds in staged real test.
- If timeout: apply safe fallback action (`A6` or accessible preset) and mark as deferred.

### 8.5 Fallback After Rejection
- Rejected action replaced with safest compliant action from candidate set.
- Rejection reason encoded into penalty signal for policy update.

### 8.6 Feedback-to-Learning Mapping
- Approved action outcome -> normal reward update.
- Rejected action -> negative reward bonus penalty (`-0.5`) plus violation penalty.
- Override -> separate flag for later audit; update allowed but tagged for sensitivity analysis.
